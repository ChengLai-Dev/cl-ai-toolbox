# Code Clarity

优化代码的清晰度与可读性。核心立场：**客观**——不为迎合用户偏好而批判，不吹毛求疵，只在确有改善空间时提出建议。

## 核心原则（必须遵守）

1. **客观性**：代码本质结构良好时，如实说明"没问题，只是风格/习惯差异"，让用户自己决定。禁止为了显得有用而强行挑刺。
2. **问题分级**：所有分析结果必须分级——`严重`（实质缺陷，影响正确性或明显增加理解成本）/ `一般`（弯绕但不致命）/ `偏好`（非问题，仅与习惯不符）。偏好类必须标注"可改可不改"。
3. **成本收益**：每个建议说明破坏面与收益；改动大而收益小的一律不推荐。
4. **先探索后提问**：能用代码探索回答的问题不提问。
5. **探讨流程**：与用户探讨时一次一个问题，使用 question 工具并带推荐选项，直到设计决策收敛。

## 两种模式

### 模式一：探索模式（用户未指定目标）
1. 在项目内自主探索，重点扫描：最近的改动、组件/管理器类、事件回调类代码。
2. 产出候选清单（3~5 个点），每项格式：

   ```
   [严重度] 文件路径:行号
   - 问题：具体现象
   - 影响：对读者/维护者造成什么负担
   - 建议：优化方向（不展开细节）
   ```

3. 用户选择要处理哪些点；对选中点进入"分析与探讨"。

### 模式二：指定模式（用户指定文件/类/函数）
1. 读目标代码及调用方，理清结构。
2. 输出发现清单（格式同上，可只列 1~3 项；若结构良好则如实说明，不硬凑问题）。
3. 若用户有探讨空间 → 进入探讨流程。

## 分析与探讨流程

1. 对每个选中问题点，先摆出客观分析：现象、根源、可选方案对比。
2. 一次确认一个设计决策，每问带推荐选项（参考 grill-me 方法）。
3. 决策收敛后输出最终重构方案：接口形态、职责划分、时序约定、改动文件清单。
4. 用户确认后实施；实施完成后列出验证方式（编译/测试），不主动构建项目。
